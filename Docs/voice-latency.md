# Задержка голосового ответа

Целевая полная задержка — от последнего слышимого кадра пользовательской
речи до первого фактически слышимого кадра Iris. Программная диагностика
приближает её: начало восстанавливается по тишине VAD, конец фиксируется
по подтверждению проигрывателя. Задержки захвата, драйвера и устройства,
а также начальная тишина аудио требуют отдельной проверки записью звука.

## Последовательность

```text
Последний кадр речи → пауза VAD → Smart Turn → STT
→ решение и сохранение → первая дельта LLM → пригодный для речи фрагмент
→ TeraTTS → транспорт и декодирование → начало звука
```

Контрольное событие — `voice.end_of_speech_to_playback`,
поле `end_of_speech_to_playback_ms`. Оно возникает один раз для выбранного
владельца звука — `unity` или `desktop_ui`. Поля
`measurement=software_playback_ack` и `origin=server_vad_estimate` обозначают
границы измерения. Время STT или синтеза само по себе не равно задержке
всего разговора; подтверждение проигрывателя не является акустическим замером.

## Текущий профиль

- Профиль `natural` передаёт кандидат Smart Turn после примерно 350 мс тишины.
  Неполная реплика продолжает собираться; консервативная защита сохраняется.
- Первый пригодный для речи фрагмент ориентируется на 24 символа,
  ожидание сброса — 80 мс. Разрез допустим на пробеле или пунктуации.
- Начало воспроизведения: один декодированный сегмент, без временного
  предварительного накопления, запас планирования 10 мс.
- Стабильные части длинной речи могут распознаваться до её окончания.
- Для подходящих прямых обращений оценка состояния идёт параллельно ответу.

Значения определяются [конфигурацией](../apps/backend/app/core/config.py) и
[`.env.example`](../.env.example); действия по голосовому пути —
в [живом разговоре](live-conversation.md).

## Как измерять

1. Запишите оборудование, модели/revisions, устройства, акустику и тип запуска.
2. Соберите не менее 30 реальных реплик и сгруппируйте новые трассы по `trace_id`.
   Для устойчивого вывода о P95 расширьте выборку и повторите сеанс.
3. Разделите первый запуск и прогретый профиль.
4. Рассчитайте P50/P95 полной задержки и отдельных стадий.
5. Сохраните отмены и ошибки отдельно; не исключайте неудобные результаты
   без явного правила.

События стадий:

```text
voice.endpoint_detected
voice.stt_completed
voice.decision_completed
voice.llm_first_delta
voice.first_speakable_segment
voice.tts_first_segment_ready
voice.end_of_speech_to_playback
```

Цель выпуска: P95 ≤ 2,5 с; рабочий ориентир прогретого профиля — P50 ≤ 1,5 с.
Это критерии приёмки, а не уже подтверждённая скорость на всех компьютерах.

## Трассировка по этапам · 7 ноября 2026

Первый этап оптимизации добавляет измерения, сохраняя модели, endpoint-паузы,
буфер Unity, фильтры и порядок исполнения инструментов. Отдельные тесты
проверяют, что получение первого текста от API фиксируется раньше его
передачи из существующего буфера native tools.

Одна трасса начинается до Smart Turn. Она связывает `session_id`, `generation`
и `candidate_id`, а после принятия реплики получает `utterance_id`.
`trace_id` сохраняется между асинхронными задачами и рабочими потоками.
Продолженная реплика может создать новый кандидат: результаты разных
кандидатов нельзя складывать в одну последовательность без проверки статуса.

| Группа | Что фиксируется |
| :--- | :--- |
| Вход | Оценка конца речи, длительность тишины, позиция PCM, частота и профиль захвата, VAD |
| Smart Turn / STT | Отдельные интервалы, вход в рабочий поток, ожидание блокировки STT; фактическое устройство и прогрев GigaAM |
| Решение | Время решения, сохранения наблюдения и подготовки памяти; ожидалась ли отдельная оценка или шла параллельно |
| Агент | Подготовка хода, построение контекста, lookup, контекст мнений и готовность prompt |
| LLM | Идентификатор физического запроса, назначение, попытка, получение заголовков, первого текста/вызова инструмента, выпуск первого фрагмента, завершение и число токенов |
| Фильтры | Причины удержания начала, выпуск после guards и проверки правдивости, первая дельта для голосового слоя |
| TTS | Постановка фрагментов, семафор, блокировки, нормализация, ударения, inference, обработка WAV, модель/revision и число потоков TeraTTS |
| Вывод | Готовность аудио, отправка WebSocket/аватару, браузерное декодирование, буфер и запас планирования; запуск владельца звука |

`input_processing_ms`, `input_max_frame_ms` и `input_max_gap_ms` — показатели
обработки и поступления кадров **за текущий сеанс захвата**. Они помогают
заметить остановки, но не измеряют возраст кадра в микрофоне или сетевую
задержку. Время запуска задачи финализации входит в оценку после VAD.
Часы браузера и сервера напрямую не вычитаются: браузер сообщает только
локальные интервалы. `base_latency_ms` / `output_latency_ms` сохраняются,
если WebView предоставляет их; они не подменяют акустическую проверку.

Длительности интервалов содержатся в событиях `phase=start/end` с `span_id`
и `parent_id`. Вложенные и параллельные интервалы **не суммируются**.
`llm.first_raw_text` — текст непосредственно от провайдера;
`llm.first_released_text` — фрагмент, который провайдер передал агенту;
`agent.first_delta` — данные, дошедшие до голосового слоя после подготовки
и проверок. Это разные границы.

### Локальный журнал

По умолчанию включены:

```dotenv
VOICE_LATENCY_DIAGNOSTICS_ENABLED=true
VOICE_LATENCY_PERSIST=true
```

`DIAGNOSTICS_ENABLED=false` отключает новые трассы. `PERSIST=false`
оставляет только ограниченную диагностику в памяти. Изменение переменных
окружения применяется после перезапуска ядра.

Журнал: `<app_data_dir>/logs/voice-latency.jsonl`, обычно
`%LOCALAPPDATA%\NeuroAsist\logs\voice-latency.jsonl`.
Запись выполняется отдельным лениво создаваемым потоком через ограниченную
очередь. Основной файл ограничен 5 МиБ, сохраняются две ротации `.1` / `.2`.
Медленный диск приводит к пропуску диагностических событий, а не ожиданию
голосового пути. Ошибки и пропуски видны в `write_errors` / `dropped_events`.
Завершение приложения ограниченно ждёт записи остатка очереди.

В журнал допускаются только заранее определённые числовые поля и короткие
технические метки. Аудио, реплики, prompt, аргументы инструментов, документы,
URL и тексты исключений в него не передаются. В инкогнито запись этого
журнала на диск запрещена; числовая диагностика остаётся в памяти процесса.

`GET /debug/voice/latency?limit=30` возвращает последние трассы и состояние
записи. В desktop действует обычная проверка токена ядра. Максимум — 120
трасс, по 256 событий в памяти на трассу; `truncated_events` сообщает об
усечении. Для длинного сеанса используйте JSONL, а не общий буфер событий UI.

### Отчёт без запуска приложения

```powershell
$voiceTraceLog = Join-Path $env:LOCALAPPDATA 'NeuroAsist\logs\voice-latency.jsonl'
.\.venv\Scripts\python.exe scripts/report_voice_latency.py $voiceTraceLog --output output/voice-latency-baseline.json
```

Ротации при необходимости передаются дополнительными путями. Параметр
`--owner unity` или `--owner desktop_ui` ограничивает путь воспроизведения.
`--since 2026-11-07T12:00:00+03:00` / `--until` выбирают трассы по времени
их начала; часовой пояс обязателен, правая граница не включается.
Скрипт читает только указанные файлы; не запускает ядро, модели и API.

Отчёт содержит P50/P95 в миллисекундах и размер каждой выборки:

- `playback` разделяет владельцев, итоговые статусы, выключенный звук и
  реплики, в которых могла прозвучать реакция ожидания поиска.
- `llm` разделяет назначения и исходы запросов, отдельно показывает первый
  текст и его удержание провайдером.
- `stages` показывает отдельные завершённые интервалы; для TTS выбирается
  первое задание, если его связь доступна в журнале.
- `intervals` показывает ожидание первого речевого фрагмента, превращение
  его в аудио, путь до подтверждения запуска и ожидание блокировок.
- `incomplete_traces`, `missing_events` и `invalid_lines` делают пропуски,
  ротацию и недописанный хвост видимыми. Отмены и незавершённые ответы
  не превращаются в успешные нулевые измерения.

Первая речь при поиске может быть лишь реакцией ожидания. Соответствующая
группа не доказывает готовность содержательного ответа по источникам.
Первые замеры после старта и прогретые сеансы собирайте отдельными файлами
или временными выборками. Старые журналы, в которых нет новых отметок,
не позволяют восстановить время первого токена задним числом.

### Приёмка измерений

Автоматический прогон проверяет перенос трассы PCM → агент → TTS →
подтверждение проигрывателя для обоих владельцев, отмены, старые поколения,
разделение clocks, отсутствие текстов и поведение медленного/недоступного
журнала. Подставные STT/TTS/LLM в этих тестах проверяют связь событий,
а не скорость установленных моделей и оборудования.

Реальный baseline требует запуска обновлённого ядра и серии разговоров
с обычным микрофоном, аватаром и устройством вывода. Отдельно проверьте
физическое начало речи записью выхода/акустики. До этого новые тесты
не подтверждают снижение задержки и выполнение целевых P50/P95.

## Срез · 23 сентября 2026

Локальные измерения на Windows с 16 логическими CPU после прогрева:

| Стадия | Наблюдение |
| :--- | ---: |
| Smart Turn v3.2 | Обычно 47–57 мс; первый измеренный вызов 175 мс |
| GigaAM v3 RNNT, записи 1,9–4,1 с | 177–256 мс |
| TeraTTSv2 `ru_f1`, 3 / 25 / 53 символа | 217 / 268 / 378 мс |
| Старый запас планирования браузера | 30 мс |

Первый внутренний chunk TeraTTS опережал готовность всего проверенного сегмента
на 24–74 мс. Медианы одной фразы при 4/8/12 потоках: 288/297/311 мс.
Эти данные не обосновывают глобальную смену восьмипоточного профиля.

## Срез · 1 октября 2026

PCM-повтор через `VoiceService` на GTX 1660 SUPER:

| Запись | Полная обработка, медиана 3 повторов | STT после остановки с предобработкой | Заранее готовые участки |
| :--- | ---: | ---: | ---: |
| 33,1 с | 762 мс | 235 мс | 1 |
| 61,2 с | 1171 мс | 476 мс | 2 |
| 130,1 с | 2898 мс | 288 мс | 6 |

Тексты совпали с GPU-базой на 35 записях. Поступление PCM было виртуальным,
кадры подавались раз в секунду. Хвост измерен одним прогоном без микрофона,
сетевой модели и playback. Локальный отчёт:
`output/stt-comparison/iris-overlap-gpu.json`; в Git он не поставляется.

Воспроизведение после подготовки [STT-корпуса](stt-comparison.md):

```powershell
.\.venv\Scripts\python.exe scripts/benchmark_voice_stt_overlap.py --manifest .cache/stt-lab/corpus/manifest.json --baseline output/stt-comparison/iris-integrated-gpu.json --output output/stt-comparison/iris-overlap-gpu.json
```

В локальной телеметрии полные вызовы adjudication занимали 1,05–1,56 с.
Это длительность вызова, а не первый токен и не полный выигрыш в динамиках.
На девяти фикстурах ограничение Smart Turn четырьмя потоками без idle spinning
снизило медианы inference с 46–65 до 24–25 мс при совпавших вероятностях.

## Следующая оптимизация

Сначала найдите доминирующую стадию в реальном разговоре.
Если задерживает первый ответ LLM, настройки TTS её не устранят.
Потоковый native TTS требует отдельной проверки непрерывности и отмены.
Уменьшение endpoint-паузы требует испытаний тихих окончаний и незавершённых фраз.
